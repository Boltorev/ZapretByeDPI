# Чек-лист 0.6.6 — Telegram-прокси на мобильном интернете

Сборка: `ZapretByeDPI-0.6.6-arm64-v8a.apk` (versionCode 19).
Проверять на телефоне, где раньше «на Wi-Fi работало, на мобильном нет».

## Почему вышла версия

В логах 0.6.5 видно: прокси поднимался, к Cloudflare уходило до 40 соединений
(`cf=41`), но `ws=0` и `down` замирал на 4,6 МБ — то есть канал открывался,
а данные не шли. Причина найдена в библиотеке: `DISABLE_SECURE` по умолчанию
включён, и весь CF-прокси ходит на **порт 80 без TLS**. У Cloudflare этот путь
сейчас не отвечает: проверено 28.11.2026 по всем 20 доменам из
`cfproxy-domains.txt` — на `:443` handshake `HTTP/1.1 101 Switching Protocols`,
на `:80` TCP-соединение есть, а ответа нет вообще. Мобильные операторы режут
порт 80 агрессивнее домашних провайдеров, отсюда «на Wi-Fi работает, на
мобильном нет».

Что сделано в 0.6.6:

- транспорт Cloudflare переведён на **TLS 443** (`SetDisableSecure(0)`),
  как в оригинальном tg-ws-proxy (`disable_secure=False`);
- прокси **перезапускается при смене сети** (Wi-Fi ↔ мобильные данные):
  старые TLS-соединения и выбранный домен после смены сети мертвы;
- watchdog больше не считает прогрессом новые соединения — только реальные
  байты вниз. В 0.6.2 из-за этого прокси висел 32 минуты с 47 соединениями
  и нулём данных;
- со второго застоя подряд транспорт меняется сам (TLS 443 → HTTP 80),
  рабочий вариант запоминается для следующего запуска;
- кнопка **«Сменить канал»** на вкладке Telegram — переключить транспорт
  вручную за пару секунд;
- в отчёт «Логи» добавлены канал, настройки и хвост нативного лога
  `TgWsProxy` (если logcat разрешён) — по нему видно, почему канал не пошёл.

## Что проверить

- [ ] **Мобильный интернет, прокси с нуля.** Выключить Wi-Fi, включить
      мобильные данные, Telegram → «Запустить». Под статусом должно быть
      «Канал: Cloudflare TLS 443». Telegram грузит сообщения и медиа.
- [ ] **В логе** после 15–30 секунд работы `down` растёт (а не стоит на
      месте при растущем `total`).
- [ ] **Wi-Fi → мобильные данные при работающем прокси.** В журнале
      «Смена сети: … -> …» и «Перезапуск прокси после смены сети»,
      прокси продолжает работать без ручных действий.
- [ ] **Мобильные данные → Wi-Fi** — то же самое.
- [ ] **«Сменить канал».** Статус меняется на «Cloudflare HTTP 80»,
      прокси перезапускается. Вернуть обратно той же кнопкой.
- [ ] **Застой.** Если канал умер (Telegram перестал грузить), через
      ~1–2 минуты в журнале «watchdog: данных нет …с … — перезапуск»,
      и прокси поднимается сам. Со второго раза меняется транспорт.
- [ ] **Спящий экран.** Разблокировать через 10–15 минут: в журнале
      «процесс был заморожен …с — таймеры сброшены», без ложных
      перезапусков.
- [ ] **VPN отдельно.** Кнопка «Подключить» (YouTube/X) продолжает
      работать и с включённым, и с выключенным Telegram-прокси.

## Что прислать, если всё ещё не работает

«Логи» → «Скачать». В отчёте важны строки:

- `telegram channel:` — какой транспорт был;
- `stats: … cf= … down= …` — шли ли данные;
- `=== TgWsProxy (logcat, хвост) ===` — причины отказов Cloudflare
  (`CF fail …`, `handshake 429`, `ws tls fail …`, `все CF домены недоступны`).

Если в `TgWsProxy` сплошные `429` — это лимит Cloudflare на общий домен;
тогда лечится только своим доменом (см. `docs/RU/CfProxy.md` в
Flowseal/tg-ws-proxy), а не настройками приложения.
